# SmartClass — how it is built

For a developer who has to change or extend it. Plain PHP 8 (no framework), MariaDB, Bootstrap 5, SweetAlert2 and a little vanilla JS.
Everything on the screen is real data from the database; there is no mock content.

## Folders

| Folder | What lives there |
|---|---|
| `pages/<module>/` | One PHP file per screen (`view.php`, `create.php`, …). A file handles its own POST, then draws the page. Modules: `auth`, `classes`, `lectures`, `assignments`, `quizzes`, `exams`, `marks`, `attendance`, `resources`, `announcements`, `events`, `forums`, `schedules`, `research`, `reports`, `students`, `teachers`, `settings`, `ai`, `profile`, `notifications`, `customers`, `email`, `branding`. `pages/dashboard.php` is the home page. |
| `includes/` | Shared code, no output of its own: `functions.php` (loads everything), `auth.php` (sign-in check + role helpers), `classes.php` (class access, quizzes, attendance rules), `grading.php`, `final_marks.php`, `ai*.php`, `privacy.php`, `i18n.php` (+ `lang/`), `ratelimit.php`, `hardening.php`, `health.php`, `mailer.php`, `push.php` (phone notifications), `backup.php`, `migrator.php`, `customers.php` / `instances.php` (hosting several schools), `onboarding.php`, `support_access.php`, `question_bank.php`. `app_header.php` / `app_footer.php` / `menu.php` draw the shell. Not served to the web (`.htaccess`). |
| `config/` | `db.php` (connection, session, security headers, which customer the request is for), `local.php` (database login + `secret_key`, written by `bin/init_local_config.php`), `instances/<domain>.php` (one file per hosted school), `install_schema.sql` (fresh install = the whole schema), `migrations/NNN_name.sql` (changes to an existing database). |
| `assets/` | `css/` (`app.css`, `dashboard.css`, `polish.css`, `theme-dark.css`, `rtl.css`), `js/` (one file per feature), `img/`, `vendor/` (Pyodide for the Python Run button). |
| `bin/` | Command-line tools: `migrate.php`, `update_all.php` (migrate every customer, backup first), `create_customer.php`, `restore_drill.php`, `backup_offsite.php` (copy the newest backup off the server), `make_staging.php` + `staging.sh`, `rotate_secrets.php`, `security_switch.php`. |
| `cron/` | `housekeeping.php` (nightly clean-up, daily summary, heartbeat), mail queue and daily e-mail jobs. |
| `tests/` | `run.php` and the `*Test.php` suites; `browser_scan.py` (phone-width scan) and `i18n_coverage.py` (English left in Pashto / Dari pages). |
| `docs/` | This file, `PRIVACY.md`, `CUSTOMERS.md`, the plans and to-do lists. |
| `uploads/`, `backups/`, `instances/<slug>/`, `sessions/`, `logs/` | Data written at run time (never in git; the web server user must be able to write them — see Settings › System check). |

## One request, start to finish

1. `pages/x/y.php` starts with `require_once includes/auth.php`. That loads `config/db.php`: it works out **which school** the request is for (the domain → `config/instances/<domain>.php`, else the original system), opens that school's database, starts the session, sets the security headers, loads `includes/functions.php`.
2. `auth.php` stops anonymous visitors (→ sign-in), signed-out or disabled accounts, and students who are not approved yet. It sets `$current_user_id`, `$current_user_role`, `$user`; helpers `isTeacher()`, `isStudent()`, `isAdmin()`, `requireAdmin()`.
3. The page checks **who may do this** (see Permissions below), handles its `POST` (CSRF first, then validation, then the change, then `redirect()` — Post/Redirect/Get; results travel in `Session::flash`), and sets `$page_title`, `$page_subtitle`, `$active_menu`, optional `$page_scripts` (files) and `$page_script` (inline JS).
4. `include includes/app_header.php` draws the shell, the page body follows, `includes/app_footer.php` closes it and prints the scripts.
5. Pashto / Dari: `i18nStart()` (called by the header) buffers the page and translates it on the way out (`includes/i18n.php`). Pages that are not HTML (JSON, downloads, PDF) are never touched.
6. `assets/js/ajax-nav.js` swaps the page body in place when a link is followed (`data-no-ajax` forces a full load).

## Security rules every change must keep

- **Every POST checks CSRF** (`verifyCsrf()`, `csrfField()`; JSON endpoints use the `X-CSRF-Token` header). `SameSite` cookies, `HttpOnly`, strict session, security headers in `config/db.php`.
- **Never trust a posted id.** Resolve it through the access helpers: `getAccessibleClass($id, $user, $role)` (a class the person teaches or is enrolled in), `teachesClassSql('c')` (SQL condition for "this teacher teaches class c"), `getUserClasses()`. A teacher sees only their own classes; the super admin is a teacher with `users.is_admin = 1` and additionally has the school-wide pages (`requireAdmin()`).
- **Database access only with prepared statements** (`$db->fetchOne / fetchAll / insert / update / delete / query` with `?` parameters). Output is escaped with `htmlspecialchars`.
- **Uploads** are checked by real file type and size (`storeUploadCheck`, `allowedUploadTypes`), stored outside the web path where possible, served through a PHP file that checks access.
- **Secrets** (API keys, e-mail password, 2FA secrets) are stored encrypted (`config/local.php › secret_key`; `bin/rotate_secrets.php`) and never shown again.
- **Abuse limits**: `includes/ratelimit.php` (sign-in, reset, sign-up, AI, uploads). **Passwords**: `includes/passwords.php` rules. **Two-step sign-in** for admins can be required. **HTTPS** can be forced (Settings › Security rules).
- **Personal data**: `includes/privacy.php` (retention, export, anonymise, delete), `docs/PRIVACY.md` says who can read what. The AI Tutor's safeguarding scan never sends harm messages to the AI.
- **AI** is always optional and always a draft: nothing is published, graded or e-mailed without a teacher. One switch turns it off for the whole school; a monthly budget stops it.

## Several schools on one code folder

`config/instances/<domain>.php` holds a school's database, storage folder (`instances/<slug>/`), support secret and base path. The original system owns the Customers page (`pages/customers/`): pause, service switches, limits, billing notes, one-time support links (the school's administrator can require approval first). `bin/update_all.php` applies new migrations to every school after a backup.

## How to add …

**A screen in an existing module.** Create `pages/<module>/name.php` from the closest existing page. First lines: `require_once dirname(__DIR__, 2) . '/includes/auth.php';`, then the permission check, the POST handler, `$page_title…`, `include app_header.php`, the HTML, `include app_footer.php`. Put anything used by two pages into `includes/`. Add a menu item in `includes/menu.php` only if people must reach it from the sidebar.

**A new module.** A folder under `pages/`, an entry in `includes/menu.php` (roles it is for), tables in a migration (below), shared code in `includes/<module>.php` required from `includes/functions.php`. Say in the file header comment what it does and who may use it.

**A database change.** Write `config/migrations/NNN_name.sql` (next number, one change set, written so that it runs once). Also update `config/install_schema.sql` so a fresh install has the same tables. Then `php bin/migrate.php` (this system) and `php bin/update_all.php` (every hosted school; takes a backup first). Never run a down-migration on live data — try it on a throw-away database.

**A setting.** `getSetting('key', default)` / `setSetting('key', value, $userId)` (table `app_settings`); give it a field on the right `pages/settings/*.php` page — nothing the administrator may want to change is hard-coded.

**Text in Pashto / Dari.** English is written in the page as usual. Add the phrase to `includes/lang/strings_more.php` (`'English' => [Pashto, Dari]`); sentences with names or numbers go into `includes/lang/rules.php` (regex + template) or `includes/lang/fragments.php` (a piece of a system sentence). Text built by JavaScript is translated in the browser from the same list (`assets/js/i18n-live.js`). Check with `python3 tests/i18n_coverage.py BASE EMAIL PASSWORD` against the staging copy.

**A live (streamed) AI answer.** Call `aiSseOpen()` in the endpoint, then the normal AI function (`aiChat` streams by itself when it was opened), and end with `aiSseSend(['done' => true, …])`; in the browser use `scAiStream()` and show the text with `scRenderAi()` (`assets/js/ai-stream.js`). The AI prompts use `aiRichFormatRules()` so answers arrive with headings, bold, colours and code.

**Running code in a lecture.** Python, JavaScript, HTML and CSS run in the reader's browser (`assets/js/code-run.js`); other languages go through `pages/lectures/run.php` to the code runner set in Settings › Code runner (`includes/code_runner.php`).

**Attendance lives in the Attendance module.** `pages/attendance/view.php` is the hub (Today list for teachers, own rates for students) and `pages/attendance/class.php?id=N` is one class's attendance (sheet, report, calendar, excuses, check-in, or a student's own record). The page's code is still `pages/classes/attendance.php`, which `class.php` loads in module mode (`ATT_MODULE`); the old class address forwards to the module (a POST to it still works). Always build the address with `attendanceUrl($classId, '&date=…')` or `classUrl('attendance', …)`, never by hand.

**A test.** `tests/NameTest.php` with `test('what must stay true', function () { … });`. Helpers: `mkUser`, `mkClass`, `client($userId)` (a signed-in browser), `anon()`, `eq`, `ok`, `contains`, `TW('db')` (the throw-away database). Run `php tests/run.php name` (one suite) or `php tests/run.php` (all; about 45 seconds). The tests run on their own database made from `install_schema.sql` and a built-in web server — the live data is never touched. A feature is "done" only when its test exists and passes.

## Working on the live system safely

`sh bin/staging.sh` serves a copy (`php bin/make_staging.php` refreshes it from live data with e-mail, AI keys and personal contacts removed; it never sends e-mail). `php bin/restore_drill.php` proves a backup restores. Settings › System check shows folders, files vs database, background jobs and recent problems.

**Phone notifications (web push).** `notify()` (includes/functions.php) creates the bell notification, queues the e-mail and calls `pushQueue()`; after the page is sent, `pushFlush()` rings every queued person's devices (`push_subscriptions`) with an EMPTY, VAPID-signed push (keys made once, private key encrypted in `app_settings`). `sw.js` wakes, asks `pages/notifications/latest.php` for the newest unread notification with the person's own cookie and shows it; signed out it shows a generic line. Devices are added in Settings › Notifications (`assets/js/push.js` → `pages/notifications/push.php`). Only real push-service addresses are accepted (`pushAllowedEndpoint`), a 404/410 answer or five failures remove a device, and a staging copy never sends. Tests: `tests/PushTest.php` with `tests/mock_push_server.php`.

**Research projects (the process).** `includes/research.php` holds every rule; `pages/research/projects.php` (list), `start.php` (student proposal), `project.php` (the running project: stages, milestones, timeline + discussion, teacher actions) and `file.php` (attachments, project people only). Flow: draft → proposed → (changes ⇄ proposed) → active → completed, or closed. Inside `active` the teacher sets milestones, the student hands in work, the teacher accepts or asks for changes; completing needs every milestone accepted and an optional 0–100 grade. Every step writes `research_updates` (the timeline) and notifies the other side (`research_update`). Tables: `research_projects`, `research_milestones`, `research_updates` (migration 055). The old reading list (`research_items`, `view.php` / `add.php`) is the "Library" tab. Tests: `tests/ResearchTest.php`.

**Long lists and Edit screens.** `includes/pager.php` is the one page control: `pagerWindow($total, $per)` for the LIMIT / OFFSET and `pagerHtml()` for the links (the filters in the address are kept). Paged now: forums, announcements, events, resources (with category / file-type / search filters), the research library and research projects; notifications and lectures have their own. Edit screens reuse the create page with `?id=` (events, timetable slots, library items) or are small pages of their own (`pages/resources/edit.php`, `pages/announcements/edit.php`, author only); the class is told what changed when an event or a timetable slot changes (`event_updated`, `schedule_updated`). Tests: `tests/ListsEditTest.php`.

**Research extras (migration 056).** `researchReminders()` (called by `cron/housekeeping.php`) sends due-soon / overdue / quiet-project notifications once per situation (`remind_soon_at`, `remind_late_at`, `stale_notified_at`); `researchDueSoon()` / `researchOverdueCount()` feed the Dashboard. Milestone templates: three built-in sets in `researchTemplatesBuiltin()` plus the teacher's own (`research_templates`). Sources (`research_sources`) come from the class Library or are typed in. `pages/research/report.php` is the printable project record. Tests: `tests/ResearchExtrasTest.php`.

**Student marks page.** `pages/marks/view.php` hands students to `pages/marks/_student.php` (the teacher's page is unchanged): a summary, one collapsible row per class (percent so far, grade, the five parts as chips, "Provisional" while parts are missing), the parts with the class average, the weakest part, and the grade rules behind "How grades work"; exam results are their own tab. A class average is shown only when at least 3 students have marks. Test: `tests/StudentMarksPageTest.php`.

**Top bar: search.** `includes/search.php` (`searchEverything`) answers `pages/search.php?q=` as JSON (limited to the person's own classes; students: published lectures / announcements only and no people; teachers also find the students of their classes; 60 searches a minute). `assets/js/search.js` turns the magnifier into a search field in the header (also the `/` key; ↑ ↓ Enter Esc) with the results dropping down under it. The header is grouped: the six shortcuts on the left (the current page highlighted with `is-current`), the tools on the right after a divider — search, PDF, language, theme, notifications, and the profile pill with the role. The Dashboard shows a "Needs you now" line built from the same list as "Needs your attention" (`.dash-now`). On phones the open field takes the whole row and the profile shows only the picture. Tests: `tests/SearchTest.php`.

**Back links.** `backUrl($default)` / `backLink($label, $default)` (includes/functions.php): the "← Back" link returns to the page the person came from when that was one of the app's own screens (a list keeps its filters and page number), else to the given default; never the same page, a sign-in page, an endpoint or another site. Every form and detail page has one (`class="back-link"`); `ob_start()` + `backUrl(ob_get_clean())` wraps an existing href. Test: `tests/ListsEditTest.php`.


**WhatsApp.** `includes/whatsapp.php` (settings `wa_*`, kinds with default en/ps/fa texts, consent on `users.whatsapp_*`, tables `whatsapp_senders/texts/queue`), page `pages/settings/whatsapp.php`, webhook `pages/whatsapp/webhook.php`, queue sent by `cron/send_emails.php`. Level 1 = `waClickUrl/waShareUrl/waButton`. See docs/WHATSAPP.md. Tests: `tests/WhatsAppTest.php`.

**Live lists and records per page.** `assets/js/live-list.js`: a form with `data-live data-no-ajax` drives the areas marked `data-live-results` — typing (after ~0.3 s), a filter select, a tab or a page link replaces only those areas, keeps the cursor, and updates the address. Paged lists take `$per = pagerPerPage()` (10, 25, 50 or 100; default 10; remembered in the `sc_per` cookie) and show `pagerPerSelect($per, $total)` at the TOP beside the filters — never under the list. Scripts that bind once at load must not be used for things inside a live area (a delete button would lose its confirmation): use `form[data-confirm]` (`assets/js/class.js` listens on the document). `assets/js/ajax-nav.js` sends a form in the bubbling phase, after the page's own handlers, so a Cancel or an inline error stops it.

**Upload size.** Files up to 14 MB: `APP_MAX_UPLOAD_BYTES` (includes/functions.php) and, because PHP's own default is 2 MB, `.htaccess` in the project folder (`upload_max_filesize 14M`, `post_max_size 20M`; works because the Apache config for /myProject has `AllowOverride All`). `maxUploadBytes()` is the smaller of the app cap and what PHP reports. Profile photos (2 MB), lecture pictures (8 MB) and CSV import (1 MB) have their own smaller limits.

**Assignments.** `pages/assignments/view.php` is the controller (every POST: delete, release, bulk grade, remind, private comment) and includes a template: `_list.php` (teacher: Needs grading / Open / Closed; student: Overdue / Returned / To do / Handed in / Done), `_detail_teacher.php` (tabs Student work / Instructions, summary tiles, class chart, results setting, student table with a Grade button) and `_detail_student.php` (instructions, one "Your work" card with one clear state and button). `pages/assignments/grade.php` is the grading screen: students left, the work in the middle (the file shown directly through `download.php?view=1`), marks / rubric / AI suggestion / feedback / "Return for changes" / private comments right; Save & next walks the class (`assets/js/grade-screen.js`). **Return for changes:** `submissions.status = 'returned'` (+ `returned_at`, `return_note`, `revision`), `returnSubmission()` in includes/classes.php; the student hands in again through submit.php (revision + 1, status back to submitted / late). Returned work is "waiting for the student": not counted as to grade, not as missing, not in the final marks. Marks of every assignment and quiz of a class are collected by `getClassGradebook()` and pooled into the marking scheme by `classFinalMarks()`. Tests: `tests/AssignmentWorkflowTest.php`.

**AI help in text boxes.** `aiWriteButton($task, '#textarea', [...])` (includes/ai_writing.php) puts the "Draft / improve with AI" button on a teacher's form (nothing for students, nothing when the teacher has no AI) and loads `assets/js/ai-assist.js` by itself. The browser sends the title, the form's other fields (`ctx`, whitelisted per task in `aiWriteKinds()`) and the class id; the SERVER reads the class's own topics and latest lectures (`aiClassContext()`) — never from the browser — so drafts fit what was really taught. Empty box → a draft; text already there → it is improved, every fact kept. Tasks: announcement, assignment, lecture, exam, event, resource, forum, class, quiz, research, feedback, reply, translate, improve. Students never get a writing helper. On the grading screen: `aiReviewWork()` (ready / needs changes + a note in the student's language, `ai_work_reviews`, `submissions.return_source`). Tests: `tests/AiWriteEverywhereTest.php`, `tests/AssignmentWorkflowTest.php`.
